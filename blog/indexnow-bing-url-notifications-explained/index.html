IndexNow and Bing Webmaster Tools: What URL Notifications Do—and Don’t Do

Set up a reliable URL-change notification workflow, verify submissions in Bing Webmaster Tools, and separate notice delivery from crawling and indexing.

Mahmoud Abdelnaby·9 min read·العربية

IndexNow is a way to notify participating search engines that a URL was added, updated, or deleted. A successful submission means the notification was accepted; it does not guarantee that the page will be crawled or indexed. Bing explicitly says this in its setup guidance. Bing’s IndexNow guide

That distinction matters. A notification is a discovery signal, not an indexing command. Keep the page accessible, useful, and technically eligible, and inspect its status in Bing Webmaster Tools after submission. Do not promise “instant indexing” to a client or treat a 200 response as proof the URL appears in results.

Check the page before sending the notification

For each changed URL, verify the published page first:

  1. It resolves to the intended canonical URL and returns the expected response.
  2. It is not blocked by a page directive or site rule that intentionally prevents crawling or indexing.
  3. The page contains the actual updated content, not a stale build or placeholder.
  4. The URL belongs to the verified host and uses the expected protocol and hostname.
  5. The change is meaningful: a new page, a substantive update, or a removal/redirect that should be communicated.

Submitting a broken or blocked page does not fix its underlying problem. For a redirect or removed URL, send the changed URL only when it reflects a real state change; make sure the destination and status code are deliberate.

Choose the submission route that fits your site

IndexNow is designed to notify participating search engines through one protocol. Bing documents both a hosted key file and URL submission, and its Webmaster Tools can show submission activity. Some content systems and CDNs already integrate the protocol; verify whether the integration is active before adding a second sender.

Bing’s URL Submission API or manual tool can serve custom or direct-to-Bing workflows. Bing’s current URL Submission page recommends IndexNow for automated notifications across participating engines, while the direct API remains an option for advanced custom setups. Check current API lifecycle guidance before building against a legacy endpoint. Bing URL submission options

Sitemaps remain useful. IndexNow and a sitemap solve related but different discovery needs. The sitemap gives crawlers a maintained list of canonical URLs; IndexNow signals a change event. A submission does not replace ordinary crawlable links, accurate canonical tags, or sitemap maintenance.

Implement the IndexNow key safely

The site needs an API key to demonstrate control of the submitted host. Bing’s setup instructions describe generating a key, hosting the matching UTF-8 text file on the same host, and submitting URLs with the correct key or key-file location.

  • Keep the key file contents exact; do not add unrelated text or formatting.
  • Host the file where the protocol expects it and verify the public URL resolves over HTTPS.
  • Keep the key value in server-side configuration or the integration’s protected settings. Do not expose secrets in a public repository, analytics event, browser log, or content page.
  • Restrict the sender to URLs from the verified site. Do not let a form field or untrusted content submit arbitrary external URLs.
  • Use an existing supported integration when it already handles key rotation, URL validation, and event timing correctly.

For a custom workflow, trigger the notification only after the final URL is live. A draft or preview URL should not enter the production notification list.

Send changed URLs, not the entire archive

Maintain an event list from the publishing system: URL, change type, publish time, and notification result. Send only URLs that changed since the integration was enabled. Bing advises against bulk-submitting years of unchanged URLs when first adopting IndexNow. For a large release, batch submissions at a controlled rate; a 429 Too Many Requests response means the sender should honor throttling rather than retry in a rapid loop.

For each request, keep the response code and a sanitized log. A successful response indicates that the request was accepted, not that the page has been fetched. Bing’s setup guide documents common request outcomes such as invalid format, invalid key, host/key mismatch, and rate limiting. Treat those as separate conditions to diagnose.

Verify submission and indexing as separate states

In Bing Webmaster Tools, inspect the IndexNow report or URL Inspection for the selected property. Track these stages separately:

Stage Evidence What it means
URL changed Publishing system or deployment record The page state changed on the site
Notification sent API response and sender log The integration attempted delivery
Notification received IndexNow activity in Bing Webmaster Tools The endpoint accepted or recorded the URL event
Crawled URL Inspection or crawl diagnostics Bingbot fetched the page
Indexed Bing index status or results inspection The page is included in the index at the time checked

Do not collapse these into one “indexed instantly” status. A URL can be submitted and still remain uncrawled or unindexed. Bing may choose not to index pages that do not meet its selection criteria. If the URL is not indexed, inspect the reported reason, page quality, canonical, robots directives, response, and internal discovery paths instead of repeatedly resubmitting the same unchanged URL. A publish-time checklist for a small site

For a small static site, an uncomplicated process is usually enough:

  1. Publish the final article and confirm the public URL loads.
  2. Confirm its canonical and internal links point to the intended page.
  3. Update the sitemap if the deployment process does not already do so.
  4. Send the changed URL through one working IndexNow integration.
  5. Save the response and check submission activity in Bing Webmaster Tools.
  6. Inspect crawl and index status later; troubleshoot a reported issue rather than resubmitting without a change.

Keep ownership of the key, integration, and deployment logs clear. If multiple plugins, a CDN, and a custom script all send notifications, check that they do not create duplicate or uncontrolled traffic. The goal is accurate change signals and diagnosable records, not the highest submission count.

Field experiment thread: validate an IndexNow publishing workflow

This is a proposed process check, not a claim that submissions guarantee indexing.

1/ Select one genuinely new or updated page and confirm the final public URL, canonical, response, and content are correct.

2/ Record the publish timestamp and change type. Confirm that the system sends only this changed URL and that no duplicate integration is active.

3/ Save a sanitized request result and check the corresponding IndexNow activity in Bing Webmaster Tools. Treat a response error separately from an indexing issue.

4/ Inspect crawl and index status after a reasonable interval. If Bing did not index the page, record its diagnostic status and inspect page quality, accessibility, canonicalization, and discovery paths.

5/ Repeat only when a new change or diagnosed fix justifies a new notification. Summarize submission, receipt, crawl, and index counts as separate measures.

Tool-neutral prompt pack: audit an IndexNow integration

Prompt 1 — Check readiness

Using only these facts [final URL, response, canonical, robots/index directives, sitemap state], identify blockers to crawling or indexing that exist before an IndexNow request. Separate verified facts from missing checks. Do not claim submission will cause indexing.

Prompt 2 — Review a sanitized request log

Classify these request outcomes [timestamp, status code, host, change type; omit API key]. Distinguish invalid format, key validation, host mismatch, throttling, accepted submission, and unknown outcomes. Suggest one diagnostic check per error. Do not repeat requests automatically.

Prompt 3 — Prepare a status report

From these sanitized records [publish events, submission responses, Bing Webmaster activity, URL Inspection status], report counts for changed, submitted, received, crawled, and indexed URLs. Keep stages separate, state the date range, and list pages whose status is still unknown.

Stop-doing swipe file: stop calling a 200 response “indexed”

Stop: “The endpoint returned success, so the article is indexed.” That response concerns the notification request, not the page’s later crawl or index status.

Say instead: “The URL submission was accepted at [time]. Bing Webmaster Tools shows [received status]. URL Inspection currently reports [crawl/index status] as of [check date].”

Stop: repeatedly submitting an unchanged page because it does not appear immediately.

Do this instead: inspect the URL, confirm its canonical and crawlability, review the reported reason, fix an actual issue if present, then notify the engine only when the page changes.
