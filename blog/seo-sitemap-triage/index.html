Triage a Sitemap That Search Tools Cannot Fetch

Check sitemap access, syntax, canonical URLs and host behavior before rebuilding the file.

Mahmoud Abdelnaby·5 min read·العربية

If a search tool cannot fetch a sitemap, first find out what the server actually returns. Rebuilding XML before checking the response can preserve the wrong cause.

Triage the request in order

  1. Open the exact sitemap URL in a browser and record the status, final URL after redirects, and content type.
  2. Confirm the response is the intended XML—not an HTML error, login page, bot challenge, or a website homepage returned with status 200.
  3. Validate the XML structure and namespace; check for escaped characters and a single valid urlset or sitemap index.
  4. Inspect a sample of listed URLs: correct host, HTTPS, canonical destination, no blocked or noindex pages, and no staging routes.
  5. Check robots.txt for the sitemap reference and test access from the verified search-tool property.

A fetchable sitemap helps discovery but does not force crawling or indexing. A sitemap should list canonical, indexable URLs you want considered; do not include every parameter variant or duplicate language route.

Separate fetch from indexing

“Could not fetch” points to retrieval or format. “Fetched, but few URLs discovered” points to content or URL selection, not necessarily sitemap syntax. “Discovered but not indexed” requires page-level inspection: canonical, crawl access, quality, and internal links. Keep these states separate in the work log.

After fixing a verified cause, resubmit once and inspect the tool’s later status. Avoid repeated submissions as a substitute for fixing access. Google’s sitemaps documentation describes requirements and limits.
